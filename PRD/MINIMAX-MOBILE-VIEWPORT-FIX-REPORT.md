# MiniMax Mobile Viewport Fix Report

**Milestone:** Bounded correction — production `web/index.html` viewport-meta regression
**Brief:** PRD/UI-POLISH-MINIMAX-TASK.md (read-only reference)
**Scope:** Single-line addition to the production HTML shell. No CSS, JSX, dependency,
or backend changes.
**Date:** 2026-09-23

---

## 1. Root cause

`web/index.html` (the production HTML shell served by Vite) was missing the
`width=device-width, initial-scale=1` viewport declaration. Without it, mobile
Safari and Chrome on Android render the page using their legacy ~980 px
"layout viewport" fallback and then shrink the whole desktop canvas to fit the
device. Every existing `web/src/index.css` mobile rule under
`@media (max-width: 767px)` was therefore unreachable on a real phone, which is
why the user-visible regression was "整個網站像桌面版縮圖".

Source-level evidence before the fix (`web/index.html` lines 1–7):

```html
<!doctype html>
<html lang="zh-Hant">
  <head>
    <meta charset="UTF-8" />
    <title>裝修進度神器 — 室內裝修 B2B2C</title>
  </head>
```

A grep across `web/src` confirmed no `viewport`, `device-width`,
`user-scalable`, or `initial-scale` declarations existed anywhere in
production code or test fixtures. (`viewport` matches in tests are descriptive
comments about scrolling sections, not meta-tag assumptions.)

A grep across `web/src/index.css` confirmed there is **no** transform-based
zoom hack, no fixed `min-width` on the body / app shell / header that would
mimic a desktop layout, and no `user-scalable=no` hiding the issue. The
existing mobile media-query contract written in
`PRD/MINIMAX-MOBILE-UI-REPORT.md` (MOB-01 … MOB-12) is still correct and now
reaches real devices.

## 2. Exact change

| Path | Kind | Notes |
| --- | --- | --- |
| `web/index.html` | Modify | Added one `<meta name="viewport" …>` line inside `<head>` after the charset. |

`git diff -- web/index.html`:

```diff
diff --git a/web/index.html b/web/index.html
index d5427cb..7920741 100644
--- a/web/index.html
+++ b/web/index.html
@@ -2,6 +2,7 @@
 <html lang="zh-Hant">
   <head>
     <meta charset="UTF-8" />
+    <meta name="viewport" content="width=device-width, initial-scale=1" />
     <title>裝修進度神器 — 室內裝修 B2B2C</title>
   </head>
   <body>
```

The declaration matches the canonical form required by `PRD/UI-SPEC.md` MOB-13
and UI-MOB-008, and the constraint in `PRD/UI-POLISH-MINIMAX-TASK.md`
("Ensure `web/index.html` declares `width=device-width, initial-scale=1`; do
not use transforms or user-scalable restrictions as a workaround for mobile
viewport calibration").

- No `viewport-fit=cover` — desktop build does not need it and adding it could
  reintroduce safe-area side effects in the existing dialog styles.
- No `user-scalable=no` — preserves the accessibility affordance described in
  `PRD/SPEC.md` and `PRD/UI-SPEC.md` §7.
- No `<meta name="theme-color">` — out of scope, and the desktop / mobile
  range does not require it.

`web/dist/index.html` (regenerated by `npm run build` during verification)
also contains the new line, confirming Vite propagates the meta to the
production bundle unchanged (`base: './'` is already set, and Vite does not
strip `<head>` meta tags).

## 6. Fixed-viewport evidence

The host environment has no real iPhone Safari or Android Chrome on a phone
form factor. The closest available evidence is headless Chromium 152 (the
container's installed browser). A self-contained probe HTML
(`<head><meta name="viewport" content="width=device-width, initial-scale=1">`
plus `@media (max-width: 767px)` and `@media (max-width: 359px)` rules that
change the body background color and a `::after` label) was served from
`web/dist/` and rendered at three viewport sizes. The probe was deleted from
`web/dist/` afterwards and is not part of the deliverable.

Captured screenshots:

| Window size | Background color | `::after` content | Indicates |
| --- | --- | --- | --- |
| 1440 × 900 | `#1f4d8f` (primary, no mobile MQ match) | "DESKTOP (>= 768px)" | Desktop layout viewport honored |
| 390 × 844 (iPhone 13/14) | `#19704a` (success), 767 px MQ matched | "MOBILE (<= 767px)" | Mobile media query active; document width equals device CSS width |
| 360 × 800 (iPhone SE / older Android) | `#19704a` (success), 767 px MQ matched | "MOBILE (<= 767px)" | Mobile media query active; document width equals device CSS width |

Screenshots are inline below as media attachments. They prove that with the
viewport meta present, the browser uses the device CSS width as the layout
viewport and the existing `web/src/index.css` `@media (max-width: 767px)`
breakpoint becomes active — exactly the precondition UI-MOB-008 calls for.

## 7. Limitations and follow-ups

- The host has no real iPhone Safari or Android device for live physical
  verification. The screenshots above are Chromium-headless evidence at
  matching CSS-pixel viewport widths, not on-device screenshots. The
  conditional `meta viewport` declaration is what produces this behavior on
  every standards-conforming browser, but a final Codex device pass at
  390 × 844 and 360 × 800 is still recommended before the production release
  is declared complete (AGENTS.md §"驗收證據 — UI 需求 … 瀏覽器 smoke test").
- No visual diff of the rendered dashboard at 390 × 844 was performed because
  the headless Chromium image lacks CJK glyphs in this container; only the
  viewport-meta + media-query conditioning was verified visually. The actual
  DOM content was verified indirectly through the unchanged `npm test` and
  `npm run build` outputs (same CSS / JS byte sizes, 438 / 438 tests green).
- This milestone did **not** alter the existing mobile CSS contract from
  `PRD/MINIMAX-MOBILE-UI-REPORT.md`. After this fix, every MOB-01 … MOB-12
  rule in `web/src/index.css` becomes reachable on a real phone; whether the
  policy criteria still hold under on-device Safari is the next layer of
  verification, owned by Codex's browser smoke pass.
- Git, Vercel, and Notion were intentionally not touched, in line with the
  explicit "不要 commit、push、部署或更新 Notion" instruction. The change
  remains in the working tree (`git status` shows `M web/index.html`).
